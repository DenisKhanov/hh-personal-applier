## Project Goal

Build `HH Personal Applier`: a Chrome MV3 extension plus a local Go backend
that automates `Откликнуться` clicks on `hh.ru` inside the **owner's own
logged-in browser session**. It is a macro on top of the live UI, not a
server-side bot, parser, or anti-detection tool.

Constraints:

- Single user, single account, single browser. Not multi-user, not SaaS, not
  for redistribution.
- Loaded into Chrome via Developer mode `Загрузить распакованное
  расширение`. Not published to the Chrome Web Store.
- The extension does not run in the background. The owner clicks Start in the
  popup; the cycle stops on any anomaly or on owner Stop.
- The local Go backend listens **only** on `127.0.0.1:8080`. It is unreachable
  from outside the host.
- LLM cover letters are part of the core scope, not a future phase.
- Telegram is used for outbound notifications and cover letter approval, not
  for control.

## Phase Discipline

Implementation order is strict:

0. Bootstrap (folders, manifests, docker-compose).
1. Backend skeleton (config, logging, postgres, migrations, health, shared
   secret middleware).
2. Extension skeleton (MV3 manifest, popup health-check, build pipeline).
3. Backend ↔ Extension API (`/candidates`, `/applied`, `/stats/today`,
   `/events/*`).
4. Content scripts: read-only parsing of search results and emit candidates to
   the background worker.
5. Auto-apply for vacancies that do not require a cover letter, with safety
   stops.
6. Telegram outbox (notifications + daily report).
7. LLM cover letters with Telegram approval flow.
8. Popup polish, run/daily limits, dashboard, end-to-end smoke.

Do not start stage N+1 before stage N's Definition of Done is met. Do not
combine stages "for convenience".

Anything not listed above is out of scope. In particular, do not add: a web
dashboard (Next.js, React), employer chats, multi-user/billing, headless
browser automation, scheduled background runs, scraping of any page outside
the active hh.ru tab.

## Red Lines (project hard rules)

These rules override convenience.

- **No anti-detection.** Do not spoof `navigator.webdriver`, randomize
  fingerprints, mask the extension presence, or simulate human-like mouse
  movement to defeat anti-bot ML. The owner uses their real Chrome; the
  extension only automates clicks.
- **No CAPTCHA solving.** If hh.ru shows a CAPTCHA, halt the cycle, send a
  Telegram alert, and wait for the owner to solve it manually and click
  Continue in the popup.
- **No proxies, no IP rotation, no headless Chrome, no residential proxies.**
- **No parsing of data outside the active hh.ru tab.** No background scraping
  of hh.ru, no parallel tabs, no reading other users' data, no cookie export.
- **No commercialization, no redistribution, no Chrome Web Store publication.**
- **No applying to vacancies that require a cover letter without explicit
  owner approval.** The cover letter is generated by LLM, posted to Telegram,
  and submitted only after the owner approves it.
- **No external runtime dependencies inside the extension.** No analytics, no
  telemetry, no SDKs that phone home. Utilities are written by hand or copied
  in source form.
- **Backend listens on 127.0.0.1 only.** Any commit that introduces `0.0.0.0`,
  a public bind, or exposes the backend behind a tunnel is a bug to be
  reverted.

## Extension Architecture Rules

- Manifest V3 with a service worker background. No persistent background page.
- Manifest permissions limited to: `activeTab`, `scripting`, `storage`,
  `notifications`. Host permissions limited to `https://hh.ru/*` and
  `http://127.0.0.1:8080/*`. Add `https://*.hh.ru/*` only if the owner
  explicitly uses regional subdomains. Never `<all_urls>`.
- `chrome.storage.local` is for bootstrap and UI cache only:
  `localBackendUrl`, `localSharedSecret`, last settings snapshot. The source
  of truth for safety settings, limits, idempotency, and counters is the Go
  backend with Postgres.
- Build pipeline is `tsc` + `esbuild`. No webpack, vite, or framework
  scaffolding.
- Popup is vanilla HTML/CSS, around 200 lines. No UI framework.
- Content script responsibilities are read-only parsing of DOM, click
  execution, anomaly detection (CAPTCHA, login lost, unknown modal). Content
  scripts must not make decisions; they only observe and execute commands
  from the background worker.
- Background worker owns the loop: pull candidates, ask backend for allow
  list, instruct content script, record outcome. Pacing lives here.
- All CSS selectors for hh.ru DOM live in `extension/src/shared/selectors.ts`.
  Selector changes are localized to that file.

## Local Backend Rules

- Listen address is **strictly** `127.0.0.1:8080`. The bind address is read
  from config but must be validated to be a loopback address; a non-loopback
  address fails config validation.
- Every endpoint requires an `X-Local-Secret` header that matches the
  `LOCAL_SHARED_SECRET` from env. The same value is mirrored into
  `chrome.storage.local`. Mismatch returns 401.
- The shared secret is generated at first install (>= 32 chars, urandom). It
  must never be committed and never logged.
- REST is built with `huma/v2` to keep typed handlers and OpenAPI generation
  consistent across the project.
- All HTTP errors follow the same shape:
  `{"error":{"code":"string","message":"string","details":{}}}`.
- The backend never reaches out to hh.ru. The only outbound calls are to
  Groq (LLM) and Telegram. Anything else is a bug.

## Browser-Side Flow Rules

- Pacing: between two `Откликнуться` clicks, wait
  `random(PACE_MIN_SECONDS, PACE_MAX_SECONDS)` from config (defaults 6-14).
  Pacing must be enforced in the background worker, not the content script.
- Run limit and daily limit are owner-configurable. Defaults: 100 per day,
  25 per Start. Limits are enforced server-side. The extension trusts the
  backend's allow list and does not maintain a parallel counter.
- Two-phase write is required even though the apply happens through the UI:
  before clicking `Откликнуться`, the backend records the vacancy as
  `attempting`. After the click outcome, the backend transitions the row to
  `applied`, `manual_action`, or `error`. If the extension or tab dies
  between record and click confirmation, the next session must not click the
  same vacancy again — the row stays in `attempting` until the owner resolves
  it manually (popup shows pending rows).
- Safety stops (any of these halts the entire cycle, alerts the owner, and
  requires manual Continue):
  - CAPTCHA detected on the page.
  - Login lost (no `Откликнуться` button and `Войти` is visible).
  - Unknown modal after the click that does not match known shapes.
  - DOM mismatch (key selectors not found).
  - Network error to backend after 3 retries with backoff.
- Daily-limit reached and run-limit reached are normal terminations: stop the
  cycle without alerting beyond the daily report.
- Stop button in the popup must abort the cycle synchronously. No "graceful
  drain" of in-flight clicks.
- The cycle starts only when the active tab is on `https://hh.ru/search/vacancy*`.
  No auto-navigation from arbitrary pages.

## Telegram Rules

- Telegram is for outbound notifications and cover-letter approval only. It
  does not control the cycle.
- All notifications go through the durable `notifications_outbox` queue. The
  dispatcher tick is around 5 seconds. Backoff on failure.
- Notification kinds: `captcha`, `error`, `daily_limit_reached`,
  `cover_letter_approval`, `daily_report`, `login_lost`. Adding a new kind
  requires a `CHECK` constraint update via migration.
- Inline buttons are used only for `cover_letter_approval`.
- The bot accepts callbacks only from `TELEGRAM_OWNER_CHAT_ID`. Any other
  chat is silently ignored.
- Daily report is enqueued at 23:55 local time by a backend cron tick.
- Do not enqueue a notification on each successful apply.

## Database Rules

- PostgreSQL 16 via Docker Compose, listening on `127.0.0.1:5432`.
- Use `golang-migrate` for migrations. Migrations are idempotent and
  reversible.
- All status-like `TEXT` fields must be guarded by `CHECK (... IN (...))`
  from the first migration. New statuses require a migration.
- Schema is intentionally small. Phase 1 tables:
  - `processed_vacancies` (idempotency + outcome log, includes `attempting`
    intermediate state).
  - `daily_apply_stats` (per-date counters).
  - `notifications_outbox` (Telegram queue with attempts/last_error/next_retry_at).
  - `cover_letters` (LLM output + approval status with TTL).
- No `user_id` columns. Single-user project; multi-user is explicitly out of
  scope. Do not add user scoping speculatively.
- `processed_vacancies` must cache enough vacancy data for the popup
  dashboard and recovery: `vacancy_title`, `vacancy_url`, `employer_name`,
  `notes`, `applied_at`.
- The pipeline file is the only place to define new statuses. Code and
  migrations follow the pipeline, not the other way around.

## LLM Cover Letters Rules

- LLM is invoked **only** from the Go backend. The Groq API key never enters
  the extension's runtime or storage.
- Provider is behind an interface: `groq` is the only implementation in
  Phase 1, but the seam allows replacement.
- Generation flow: extension reports a vacancy that requires a letter →
  backend calls LLM → applies `cover_letter_guard` (regex + length) with up
  to 3 retries → persists to `cover_letters` with `status='pending_approval'`
  and `expires_at = now() + COVER_LETTER_TTL_HOURS` → enqueues Telegram
  approval message with inline buttons.
- Approval flow: Telegram callback updates `cover_letters.status` to
  `approved` or `skipped`. The extension polls
  `GET /cover_letters/{vacancy_id}` every 5 seconds while waiting. On
  `approved`, the content script fills the textarea and clicks Submit. On
  `expired` or `skipped`, the vacancy is recorded as `manual_action` /
  `skipped` and the cycle moves on.
- `cover_letter_guard` content rules and prompts are ported from sections
  §11–§13 of the frozen predecessor pipeline. Treat that material as
  reference; do not depend on its code.
- Rate-limit fallback: on Groq rate-limit, send one Telegram alert and skip
  letter-required vacancies until the next Start. Do not retry the same
  letter forever.

## Testing And Verification

For each implementation task, add or run the narrowest meaningful tests.

Backend unit tests should cover:

- Config validation, including loopback-only bind check and shared secret
  length.
- `X-Local-Secret` middleware.
- `/candidates` filtering by `processed_vacancies` and remaining daily limit.
- `/applied` write + counter increment atomicity.
- `cover_letter_guard` (regex + length).
- Telegram outbox dispatcher behavior with a fake telegram client.

Backend integration tests should cover:

- `processed_vacancies` idempotency with real Postgres.
- `notifications_outbox` retry/backoff and failed-after-N-attempts behavior.
- LLM through a mock provider.

Extension testing is mostly manual:

- Selector smoke: pick 10 random vacancies from a real hh.ru search and
  confirm the parser extracts them correctly. Re-run after each hh.ru DOM
  change report.
- CAPTCHA stop path: trigger or simulate a CAPTCHA shape and confirm the
  cycle halts and the alert lands in Telegram.
- Login lost: log out of hh.ru mid-cycle and confirm the cycle halts.
- Cover letter: one vacancy that requires a letter, end-to-end through
  approve.
- Do not run automated browser tests against hh.ru. Headless smoke against
  hh.ru is forbidden by the red lines.

Before final response after code changes:

- Run `go fmt`, `go vet`, and the backend unit tests.
- Run `tsc --noEmit` and `eslint` on the extension.
- Run broader tests when shared behavior changed.
- Report any tests that could not be run.

## Logging And Secrets

- Use structured JSON logs in the backend (`slog`).
- Never log: `LOCAL_SHARED_SECRET`, `LLM_API_KEY`, `TELEGRAM_BOT_TOKEN`,
  full cover letter bodies (only length and a short prefix).
- Redact or hash any personal data passing through.
- Extension logs go to `console.log` in the popup DevTools and are not
  forwarded anywhere.
- Postgres logs stay in the local Docker container; do not ship them.
- No analytics, no telemetry, no remote logging.
